# XGBoost 调参文章对当前项目的适用性评估

## 1. 一句话结论

这篇文章对当前 CS 回合胜率项目 **有帮助，但主要帮助理解参数、解释结果和设计下一轮
实验；它不能证明模型是否更换，也不能直接替代当前项目的验证流程。**

文章可以解释为什么 XGBoost 与 LightGBM 即使已经真实更换，仍可能给出高度接近的
概率。是否换模成功仍应由模型类、工件哈希、参数、逐回合预测和指标复算证明，完整
证据见 [模型更换验证报告](05_post_first_kill_model_replacement_verification.md)。

## 2. 适用性评分

| 用途 | 帮助程度 | 判断 |
|---|---|---|
| 理解 XGBoost 参数 | 高 | 参数分组和过拟合解释清楚，适合作为入门材料 |
| 解释 XGBoost/LightGBM 为何接近 | 高 | 两者都是 GBDT，使用相近复杂度控制时可能学习到相似函数 |
| 直接提升当前冻结模型 | 中低 | 通用建议需要转化成 `series_id` 分组验证实验后才能判断 |
| 证明模型是否换成功 | 无 | 文章不能检查本地工件、哈希和原始预测 |
| 改进报告与可视化 | 中高 | ROC、混淆矩阵、重要性和 PDP 可作为起点，但需补校准与不确定性 |
| 直接复制示例代码 | 低 | 普通随机行切分不适合有关联的电竞回合数据 |

因此，正确用法是“吸收分析框架”，不是“照抄信用风险案例重新训练”。

## 3. 能直接帮助当前项目的部分

### 3.1 用参数组解释模型行为

文章把参数分成学习速度、模型复杂度、随机性和正则化，这个框架很适合解释当前工件：

| 作用 | XGBoost 参数 | 当前项目应回答的问题 |
|---|---|---|
| 学习速度 | `learning_rate`、`n_estimators` | 每棵树修正多少、validation 在第几棵树停止 |
| 树复杂度 | `max_depth`、`min_child_weight`、`gamma` | 是否学习了过细、只在少数比赛成立的模式 |
| 随机性 | `subsample`、`colsample_bytree` | 是否过度依赖某些系列赛或特征组合 |
| 正则化 | `reg_alpha`、`reg_lambda` | 是否抑制不稳定叶节点和过拟合 |
| 类别不平衡 | `scale_pos_weight` | 是否改变分类边界，以及胜率概率是否仍校准 |

XGBoost 官方调参说明同样把控制复杂度与增加随机性作为两类主要过拟合控制方法，并
提醒降低 `eta` 时通常要增加 boosting 轮数，见
[XGBoost 参数调优说明](https://xgboost.readthedocs.io/en/latest/tutorials/param_tuning.html)。

当前 XGBoost 与最终 LightGBM 都采用 `learning_rate=0.03`、相近的行列采样、L2 正则
和较保守的树复杂度。文章因此能帮助解释：两个不同实现学习到相似概率并不异常。

### 3.2 提醒不能只看 Accuracy

当前产品展示的是“胜率概率”，不仅是最终胜负分类。文章提醒不能只看 Accuracy，这与
项目方向一致，但当前项目还应比文章更进一步，同时使用：

- Log Loss：惩罚过度自信的错误概率；
- Brier：衡量概率与 0/1 结果的平方误差；
- ECE 与可靠性曲线：检查“预测 70%”是否真的约有 70% 获胜；
- AUC：检查排序能力；
- Accuracy：作为固定 0.5 阈值下的辅助指标；
- `series_id` 配对 bootstrap：判断模型点差是否超过系列赛间波动。

当前五项配对区间全部包含 0，因此文章最有价值的提醒不是“继续调到一个模型获胜”，
而是“不要只盯着一项点指标”。正式比较见
[首杀后 LightGBM 报告](04_post_first_kill_lightgbm_report.md)。

### 3.3 理解学习率和树数的联动

文章指出较低学习率通常需要更多树，这有助于理解当前 XGBoost 的 409 棵有效树与
LightGBM 的 211 棵部署树。但两个库采用不同生长策略，树数不能直接比较大小。

LightGBM 官方文档说明其采用 leaf-wise 生长，`num_leaves` 是主要复杂度参数，设置
`max_depth` 后也应一起约束 `num_leaves`；简单把 depth-wise 与 leaf-wise 的深度或
叶数一一换算并不可靠，见
[LightGBM 参数调优指南](https://lightgbm.readthedocs.io/en/latest/Parameters-Tuning.html)。

因此，公平方法是让两者都使用固定 validation 早停和相同模型选择指标，而不是要求
相同树数。

### 3.4 支持分阶段调参

文章建议先建立稳定基线，再逐组控制复杂度、随机性和正则，最后联合学习率与树数。
这个思想能让每次变化有明确解释。当前 M29 已采用 validation-only 的 9 阶段、36 候选
调参流程，并冻结了 test 不参与选择的规则，因此不需要为“跟文章一致”而重做已有
模型。

文章真正带来的下一步是：若要再比较算法，应预先给 XGBoost 和 LightGBM 相同的搜索
次数、种子数、早停规则、选择指标与计算预算。

### 3.5 扩展诊断图

文章中的 ROC、混淆矩阵和特征重要性可以保留，但对当前项目还应加入：

- XGBoost–LightGBM 概率散点图和 `y=x` 参考线；
- 两模型绝对概率差分布；
- 29 个阈值分类分歧回合；
- 两个模型都高置信但预测错误的回合；
- 可靠性曲线及每个概率箱样本量；
- 分地图、阵营、经济档位的误差与校准；
- 指标点差及 `series_id` 配对 95% CI 森林图；
- 多随机种子的特征重要性稳定性。

这些图比单独展示 Accuracy 或一张 importance 图更能回答“模型哪里相同、哪里不同”。

## 4. 只能作为入门理解的内容

以下内容有教学价值，但不能作为当前项目的正式验证证据：

- “后一棵树不断纠正前一棵树”的老师类比；
- 二阶泰勒展开和 split gain 的简化推导；
- 人工生成的信用风险样本；
- “AUC 超过某个经验值就很好”的通用判断；
- 一套固定的万能调参顺序；
- 单次 Feature Importance 排名；
- 单个特征的 PDP 曲线。

另外，文章对 `min_child_weight` 的口语化解释不能理解成简单的“叶子里最少样本数”。
XGBoost API 将它定义为子节点内实例权重（Hessian）之和的下限，见
[XGBoost Python API](https://xgboost.readthedocs.io/en/stable/python/python_api.html)。

## 5. 不能直接照搬的做法

### 5.1 普通随机按行切分

文章示例使用普通 `train_test_split`。电竞数据中，同一系列赛的地图和回合高度相关；
随机按行切分可能让同一系列赛同时进入 train 和 test，造成数据泄漏和过于乐观的指标。

当前按 `series_id` 分组的 70/20/10 split 必须保留。回合数虽有 4,170，但统计不确定性
应以 79 个完整测试系列赛为单位，而不能假设 4,170 个回合完全独立。

### 5.2 只有 train/test，没有独立 validation

参数、早停和校准都必须只使用 train 与 validation。test 只能在协议冻结后用于最终
评估，不能看过 test 后再返回调参。当前 M28–M33 已遵守这条规则。

### 5.3 直接相信 Feature Importance

装备价值、现金、步枪数、AWP、比分和阵营信息存在相关性。树的重要性可能把共享信息
集中给其中一个变量，不能解释成因果关系。更适合当前项目的是：

- 原始特征分组 permutation importance；
- TreeSHAP 分布而不是只看单个样本；
- 多随机种子的排名稳定性；
- 预先定义的特征组消融实验；
- 把解释写成“模型关联因素”，不写成确定战术因果。

### 5.4 对相关特征直接使用 PDP

PDP 会改变一个特征并对其他特征边际化。当特征高度相关时，它可能构造比赛中根本
不会出现的经济与装备组合。scikit-learn 官方文档也明确提示相关特征可能产生不合理的
合成数据点，见
[PDP 与 ICE 文档](https://scikit-learn.org/1.9/modules/partial_dependence.html)。

可优先使用真实数据分组曲线、ICE、ALE，或限制在真实样本邻域内做敏感性分析。

### 5.5 盲目使用类别权重

`scale_pos_weight` 可能改善某个分类阈值，却改变概率含义。由于本项目要显示胜率，任何
类别权重实验都必须重新检查 Log Loss、Brier、可靠性曲线和 ECE，不能只看 AUC。

### 5.6 复制文章参数

信用数据的参数不能直接迁移到 CS 比赛。参数是否有效必须通过当前数据的分组 validation
判断；为了让 LightGBM 与 XGBoost 输出“看起来更不一样”而调参，属于错误目标。

## 6. 文章如何帮助解释“两模型太接近”

文章本身不能检查本地模型，但它提供了合理机制：

1. 两者都是加法式梯度提升树；
2. 使用完全相同的数据、标签、预测时点和 40/82 特征；
3. 学习率、采样与正则化方向接近；
4. 最终模型都偏向保守复杂度；
5. 首杀阵营、双方装备和经济等主要信号对两个算法都很明显。

所以两者概率相关系数达到 0.998928 并不自动表示错误。真正证明它们不同的是模型类、
内部工件、SHA256、树数、逐回合概率和阈值分歧，而不是强行要求指标拉开差距。

## 7. 建议吸收文章后进行的实验

### 优先级 A：模型来源与复现清单

每次训练继续保存：模型库与类、库版本、完整参数、模型 SHA256、数据 SHA256、split、
特征名称与顺序、随机种子、最佳迭代、预测文件和校准方法。当前项目已经覆盖大部分，
后续界面只需把这些信息可视化。

### 优先级 B：同预算、多随机种子公平比较

预先冻结相同搜索次数、主要选择指标、早停规则和 5 个固定随机种子。报告每项指标的
平均值与标准差、模型间预测相关性和特征排名稳定性。如果种子波动大于算法点差，就应
报告“算法差异缺乏实际意义”。

### 优先级 C：模型分歧回合审计

优先复查：

- 当前 29 个 0.5 阈值分歧回合；
- 绝对概率差最大的 20–50 个回合；
- 两模型都高置信但错误的回合；
- 不同地图、阵营和经济阶段的系统性误差。

这比继续比较千分位 AUC 点差更可能发现真实的数据或特征问题。

### 优先级 D：特征组消融

建议依次比较“比分/地图基础特征”“+经济”“+装备”“+首杀信息”“完整模型”，确认性能
来自哪些信息，并检验首杀后模型是否真正利用了首杀新增特征。

### 优先级 E：负对照与时间外测试

- 打乱 train 标签后，AUC 应回落到接近 0.5；
- 逐项证明特征在预测截止时间已经可获得；
- 如数据允许，用更晚赛事或版本做 out-of-time 测试；
- 不把现有随机系列赛 split 的结果直接外推到未来比赛版本。

## 8. 最终建议

文章值得作为“XGBoost 参数理解和实验设计入门材料”保留，但不是重写当前模型的理由。
当前应保留 `series_id` 切分、validation-only 调参、冻结 test、五项概率指标和配对
bootstrap，并把文章的价值转化为同预算稳健性实验、模型分歧审计和更完整的可视化。

如果完成这些实验后两者仍然非常接近，正确论文结论应是：**在当前数据、特征和验证
设计下，两种 GBDT 没有可确认的性能差异。** 不需要人为制造一个胜者。
